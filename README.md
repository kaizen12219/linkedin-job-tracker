# Job Tracker → ApplicantAlly

This extension captures qualifying LinkedIn and Jobright jobs into ApplicantAlly. Research uses independent Codex sessions in Rezi Builder; saving and duplicate checks use ApplicantAlly’s local JSON store.

Current release: **0.8.4**. See [CHANGELOG.md](CHANGELOG.md) for changes and the versioning policy. Future releases increment the patch version for fixes, the minor version for compatible features, and the major version for incompatible changes.

## Install and start

1. For first-time setup, open ApplicantAlly once to prepare its app-folder store. It may then be closed.
2. Extract the extension ZIP into a permanent folder.
3. Open `chrome://extensions`, enable **Developer mode**, and choose **Load unpacked**. Use **Reload** after updating an existing installation. The bundled public manifest key keeps the extension ID stable.
4. Open the popup’s **Folder settings** and choose the extracted ApplicantAlly app folder or its `data/workspace` directory.
5. On Windows, run `scripts/install-research-helper.cmd` once, reload the extension, and click **Start / reconnect research** in its popup. Keep Codex signed in. The helper can start the worker again after a PC reboot without editing source files. `scripts/start-research.ps1` remains available for manual startup.
6. Open LinkedIn jobs or sign in to Jobright and open your job recommendations. Capture a job. Profiles, duplicate checks and saves use the selected folder directly.

Chrome and SunBrowser use separate extension installations and browser-profile settings. If LinkedIn is in SunBrowser and Jobright is in Chrome, install or reload the updated extension in **both**, and choose the ApplicantAlly folder in each popup. Sign in to each site in the browser where it will collect. Signing in through Codex's in-app browser does not install or authorize the tracker in Chrome or SunBrowser. Each browser profile can run up to two collectors independently. Both installations can use the same local research worker; model/level choices and folder permission are stored per extension profile, and each queued job retains its own frozen settings.

The popup’s **AI research model** and **Reasoning level** selectors load choices from the signed-in session’s catalog. Levels such as Medium, High, Extra high and Ultra appear only when the chosen model supports them. Choose a model or **Session default** and a level or **Automatic**, and use **Refresh models** after changing accounts or when choices change. Automatic retains the existing research default (Extra high when supported). Switching models keeps a supported level and resets an unsupported level to Automatic. These settings apply to new job sessions. Each queued capture freezes its model and level, and retries and recovered sessions retain both. Discovery uses the existing local research worker; profile reads and saves continue to use ApplicantAlly’s folder directly.

**Start / reconnect research** starts the existing worker in the background and reloads the model list. Closing the popup does not stop the worker. The installed helper accepts only start/status requests from this extension, and leaves an already-running worker alone. If another service occupies port 8787, it reports the conflict without stopping that service. It has no job-store or profile-data API. Installation registers the helper for the current Windows user and pins the local Node runtime and research folder; if those files move, rerun the installer with the current paths. The default worker folder is `D:\rezi-builder-mcp\rezi-builder-mcp`; an alternate folder can be supplied to `scripts/install-research-helper.ps1 -BuilderRoot <folder>`.

Jobs, results, and résumé links are stored in ApplicantAlly’s app-folder data. In the extension popup, open **Folder settings → Choose folder** and select your extracted ApplicantAlly folder or its `data/workspace` directory. Chrome remembers the folder handle. The tracker reads profiles and duplicate records and writes new job files directly, including while ApplicantAlly is closed. ApplicantAlly watches these files when open and loads them on startup. Google Sheets receives a snapshot only when you use ApplicantAlly’s publish button.

## Capture a job

Jobs that are skipped or cannot be saved produce readable JSON files in the selected ApplicantAlly workspace under `job-tracker-reports/not-saved/<request-id>.json`. In a normal app installation this is `data/workspace/job-tracker-reports/not-saved`. Reports contain the captured job description and source URLs, stage and exact reason, model and reasoning level, selected profile when resolved, AI decision/evidence, redacted research prompt and rejected callback details. Local exclusions, duplicate/banned companies, unconfirmed details, research failures, expiration, cancellations and save errors are distinguished. Card-only failures say `detailAvailability: unavailable` when the full description could not be verified.

Temporary research/capacity and folder-write outages use `status: pending` and `willRetry: true`; a later confirmed save updates the same report to `status: saved` and retains its failure history. If report-file writes are unavailable, a durable Chrome outbox retries when the original folder becomes accessible. Reports stay with their original destination. Logging errors do not change a capture's outcome. The research worker also retains per-session diagnostics under its `.job-tracker-research/reports` folder, including rejected callbacks that the AI later corrects. An AI `decision: save` there means research approved the job; the extension determines whether the file was actually saved.

Click a LinkedIn search-result card to select it and start capture. The tracker waits for that exact job's details to finish loading. Once that click authorizes capture, switching tabs or covering SunBrowser does not pause the handoff. The exact job identity, changed description, stable details and ten-second expiry still apply. It preserves the existing native × dismissal behavior, and skips duplicate/banned companies. Automatic dismissal, native buttons, modified clicks, and synthetic page clicks do not start capture.

Every capture, including popup Save and the keyboard shortcut, uses this order:

1. Skip clear excluded nonengineering titles such as Business Analyst, Data Analyst, Product/Project Manager, Scrum Master, recruitment, sales, IT support and manual QA. Only mid-level and Senior engineering roles qualify. Associate and entry-level roles, including Junior, graduate/new-grad, intern, trainee and apprentice positions, are excluded. Clear titles and explicit assignments to this position are skipped locally; AI assesses ambiguous entry-level scope and mixed-level vacancies. Degree requirements, junior colleagues, numbered titles, low required years and no minimum years do not establish entry level by themselves. Skips retain their specific reason in the failure reports. Clear Staff, Principal, Distinguished, Fellow, Chief and higher engineering management titles, and descriptions explicitly assigning this position a higher level, are skipped locally, including queued captures. Lead roles, including Technical Lead, Tech Lead, Team Lead, Engineering Lead and Lead Engineer, are excluded regardless of hands-on duties or years. AI also excludes recurring team-lead responsibilities under generic titles. Senior individual contributors can mentor, lead individual projects and collaborate with Leads without becoming a Lead role. AI evaluates ambiguous titles such as Architect, Founding Engineer and numbered ranks using the actual duties, decision-making authority, company ladder and scope across teams. Team-level design, mentoring and complex independent delivery can remain Senior; working with higher-level colleagues does not give this role their level. Every remaining job starts its own AI session and requires eligible software, web, mobile, infrastructure, data/AI or software-test engineering classification with an exact 24–2000 character description quote. Above-Senior, unclear or nonengineering results skip before remote checks, profile analysis and application/contact research.
2. Read the selected job's workplace pill. **Hybrid**, **On-site**, and missing/unrecognized labels start their own research session. The session reads the description and checks for explicit fully remote work without required office attendance. If that check fails, it returns skip through MCP and stops before Easy Apply research. No local text filter rejects these jobs before a session starts; the returned evidence is checked before any central-store save.
3. For **Easy Apply**, research the exact company/title for a currently open, free external application page, a published application email, or the named job poster's published work email. Prefer the employer's careers page or authorized ATS. A job-specific page inviting email applications also counts as an application page when research verifies the current invitation, published address, employer/recruiter and a distinctive description passage of at least 100 characters matching the captured vacancy. Only this same-vacancy email route can accept an alternate displayed title. Reject LinkedIn destinations and redirects, paid/gated application routes, expired postings, generic careers/contact pages, unrelated roles, and guessed/private emails.
4. Save only when the required checks pass. A verified external application page, including an email application page, replaces **Apply URL**. The complete original LinkedIn job URL, published emails, and any remote-work confirmation go in **Info**. Do not repeat the application page URL in the email's source suffix. Other email sources remain in Info; an email without a verified application page retains the existing Apply URL as a reference. Ordinary Remote jobs with an external Apply button save only after the role classification passes.

Each new job passing the title exclusions creates its own persistent local Codex session titled `Job research · Company · Role`. Retries of the same pending request recover that job's session; different jobs never share a session. The session returns structured findings using the research worker’s `complete_job_capture` MCP tool; it cannot call resume, validation, application-answer tools, or change a destination. After rechecking the banned list, the extension checks the current folder records and commits a `capture-<requestId>.json` job file with its selected profile and Pending status. ApplicantAlly assigns the permanent job ID when it loads the capture. Failed checks add nothing.

Start the research worker on this PC at `http://127.0.0.1:8787`, and keep the Codex desktop account signed in. From this repository, run `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-research.ps1`. ApplicantAlly can be closed. Open the updated app once to prepare its file-store descriptor before first choosing the folder. Reload the extension and open LinkedIn/Jobright tabs after updating. Research uses the signed-in account’s normal usage allowance; it does not purchase anything or apply to jobs.

In LinkedIn's job details panel, click the **job title** to copy the title or the **company name** to copy the company. A dotted underline on hover and a brief confirmation identify the copy action. Tab to either field and press Enter or Space to copy with the keyboard. Modified link clicks keep their normal navigation behavior. Search result cards retain their existing selection and dismissal behavior.

Open a LinkedIn or Jobright job and select the extension. **Scrape** reads the company, job title, description, and real application URL. Review or edit the fields in this order: Company → Job title → Apply URL → Profile → Job description, then choose **Save**. Company, title, and description are required.

On Jobright, use `/jobs/recommend` results or a `/jobs/info/…` job page. The tracker reads the selected job's details and the committed search-location filter in the top bar. An employer address, another result's location, or a country typed but not applied to the search cannot determine the profile. Set and apply the search country to **United States** to use the same Kevin Lee/Jagjeet Wani routing as LinkedIn. Jobright captures with an unknown or non-US committed country are rejected; a manual profile cannot bypass this check. LinkedIn's existing region and manual-profile behavior remains available. A captured public external Original Job Post link follows the same ordinary Apply rules as LinkedIn, including role, remote and experience checks. If only a portal reference or unusable original link is available, AI must verify an external application route or the existing published-email route. The tracker does not click Apply, submit an application, or fill application forms.

New jobs use a permanent local job ID, status `added` (Pending), no application date, and **Job Tracker** attribution. Profile choices come from ApplicantAlly’s local settings. A blank Profile is allowed and remembered for the shortcut. Temporary save failures retry the same capture ID so a lost response cannot create a duplicate.

`Ctrl+Shift+Y` scrapes and saves the active LinkedIn or Jobright job without opening the popup. Change the shortcut at `chrome://extensions/shortcuts`. **Copy JSON** and **Apply URL** remain available.

ApplicantAlly’s profile data lives in `<app folder>/data/workspace/profile-library`: `settings.json` stores the current choices, `registry.json` is the generated manifest, and `snapshots/` contains the profile JSON revisions. The tracker reads enabled IDs and display names directly from `settings.json` on every options read and before a save, using `registry.json` for older folders without settings. Changed labels, disabled profiles and new IDs are picked up with ApplicantAlly closed. Full profile contents remain in the app library; the job stores the selected profile ID.

Profile selection for AI-approved eligible roles follows the country selected on the job-search page, including LinkedIn's visible country dropdown or Jobright's committed top-bar location filter. On LinkedIn, **United Kingdom → Michal Stefanow; Colombia or LATAM → Jose Ibero.** Jobright requires a committed **United States** search country. For **United States** on either site, AI extracts required engineering experience: **5+ years → Kevin Lee; below 5 → Jagjeet Wani**. Use the lower bound of a required range and ignore preferred years. When required years are absent, a Senior/Architect title or AI-confirmed senior technical scope selects Kevin; ordinary/mid-level scope selects Jagjeet. Lead, Associate/entry-level and above-Senior roles remain excluded regardless of profile or required years. “No minimum years” uses the scope fallback rather than zero. The current two-page profile ID is preferred when available; older profile IDs remain compatible.

The search country dropdown takes priority over stale URL state, and committed URL filters take priority over an unsubmitted location-input edit. Captures never infer the search country from an employer address, job description, or another card. Other LinkedIn regions retain the manual profile; Jobright rejects unknown and non-US countries. Known-region routing overrides the remembered manual choice without overwriting it. Each capture freezes its selected country and resolved profile for retries. US analysis uses the existing research session and an exact captured-description quote. All profiles save as **Pending**; automatic Trash is removed, including old queued Kevin flags.

## Collect a search automatically

On LinkedIn job search results or Jobright recommendations, press **Ctrl+Shift+U** to start collecting active jobs from the top of the current results page. Up to **two tabs** can collect automatically at the same time in one browser profile, including one LinkedIn tab and one Jobright tab. Start the first, switch to the second results tab, and press the shortcut again. A third start is rejected while both existing runs continue.

On a collecting tab, **Ctrl+Shift+U** or **Escape** stops only that tab's run. On another eligible results tab, the shortcut starts that tab if a slot is available. From an unsupported page, **Ctrl+Shift+U** stops all collectors in that browser profile. Changing the ApplicantAlly destination in Folder settings also stops all collectors in that profile. Each run has separate search/filter context, attempted-job history, progress and cancellable waits; stopping one does not cancel the other's work or research already submitted.

Collection continues when you switch tabs, use another app, or minimize Chrome or SunBrowser. Keep the browser and job-results tabs open. Collection runs without a progress panel or per-job messages. Only start/stop/completion alerts, warnings and errors appear, and each disappears after five seconds. You can change the shortcut at `chrome://extensions/shortcuts`.

Jobright collection scrolls the recommendations feed to load more cards and continues until the feed ends. It uses the same duplicate/banned-company checks, per-job research sessions, model/reasoning settings, profile routing and failure reports. It waits for the selected card's exact job details before capture. Incomplete details, repeated cards or a loading failure cannot authorize a save. LinkedIn's native × dismissal behavior described below applies to LinkedIn only.

The collector skips duplicate/banned companies, jobs already processed in the run, and cards captured manually earlier in that tab. On LinkedIn it also skips native grey/dismissed cards and Undo controls, and selects each active card using the existing native **×** dismissal behavior. Its own × turning the selected card grey or removing it does not cancel that job's save. Jobright selects active feed cards without LinkedIn's dismissal actions. On both sites the tracker waits for that exact job's header and description to settle, then pauses for a short review before using the existing save action once. The selected title's job link identifies the details in layouts with either a heading or a standalone title link; a changed search URL alone never proves the identity. Actions are separated by random 0.45–1.25 second pauses. Review pauses vary with description word count and random timing, bounded to 5–45 seconds. These are half the previous pacing delays; readiness checks and loading timeouts retain their existing limits. Each qualifying research request uses its own session and the existing `complete_job_capture` callback. After a research request is accepted, collection moves on while AI finishes in the background.

On LinkedIn, the results column scrolls to discover more cards, then the collector uses **Next** until the last results page. Lazy-loaded cards are checked before pagination. Jobright scrolls its recommendations feed until no more results load and does not use LinkedIn's Next control. A repeated page, a blocked click, incomplete job details, or a failed loading transition cannot authorize a save. If the research worker is temporarily unavailable or busy, jobs remain durably queued and collection continues; submission retries about every 30 seconds while Chrome is running, using the same request IDs. A queued job is not a saved job: it still needs successful AI checks before writing to ApplicantAlly. Temporary local-store outages keep verified research queued; saves retry with the same request ID, so a lost response cannot duplicate a job. LinkedIn's native duplicate/banned X dismissal is suspended during collection so it cannot race the paced selections.

Collection delays run in the extension worker in cancellable intervals of at most 20 seconds, so hidden-page timer throttling does not stretch every polling or review interval. Delays use elapsed time; each wake rechecks job identity and never catches up by firing a burst of clicks. Each collecting tab holds its own Web Lock to protect its active work from Chrome's automatic freezing. Each tab temporarily disables automatic discarding and restores its previous preference when its run ends. Background scrolling is immediate so hidden-page animations cannot block selection. All page-overlay and exact-job checks still apply; collection never activates a tab or brings the browser to the foreground.

Changing a tab's search or manually operating its job/navigation controls stops that tab's run. Progress in Chrome session storage lets a normal LinkedIn Next-page navigation or worker restart continue each run without replaying attempted jobs; closing a tab ends only its run, and Chrome clears [session storage](https://developer.chrome.com/docs/extensions/reference/api/storage#session) when the browser restarts or the extension reloads. Reloading the extension stops its collection runs. Research requests already submitted continue through the existing validation pipeline after collection stops. Closing the browser or putting the PC to sleep stops browser execution; collection requires its browser to remain running.

## Duplicate and banned-company behavior

Company matching trims/collapses whitespace and ignores case. A matching recorded company blocks another save regardless of its ordinary lifecycle status. The only exceptions are:

- a job in local Trash;
- `trashed` or legacy `deleted` status;
- `clearance`, `location restriction`, `location-restriction`, `on-site`, `onsite`, `language`, `not applicable`, `not-applicable`, or `restricted`.

The authoritative duplicate check runs again immediately before every write. LinkedIn search cards are classified for automatic dismissal using a short cached snapshot of the local store.

**Banned companies** remains a separate editable list. It uses Chrome synced storage when available, and Export/Import can transfer it across unrelated profiles or PCs. Duplicate and banned cards retain LinkedIn's native appearance; the tracker adds no dimming or custom card styling. Banned companies cannot be saved until removed from that list.

Duplicate and banned search results are automatically dismissed by clicking LinkedIn's own **Dismiss (×)** button as soon as classification confirms them, one job at a time with no intentional dismissal delay. The tracker acts only in a visible tab on an uncovered, on-screen dismiss button. Scroll to bring more results into view. It rechecks the current company classification and job identity before clicking, skips disabled or missing buttons, and attempts each job only once per page session. LinkedIn controls the resulting dismissed state and its Undo action.

On LinkedIn, click any open job card—active, duplicate, or banned—to select it normally, then click its native × button after the original click finishes. The tracker lets the original click reach LinkedIn and rechecks the card before dismissal. Manual card clicks do not wait for a company lookup and work before local classification or when ApplicantAlly is offline. Automatic closing applies only to duplicate and banned jobs, without random pauses. Once × has been clicked, either directly or by the tracker, clicking the card does not click × again during that page session. Native controls such as Undo keep their normal behavior.

## Save safety and limitations

Pending research requests survive worker/browser restarts and are checked about every 30 seconds while Chrome is running. Offline research submission retries with the same request ID. Temporary model errors, including capacity, overload and rate limits, remain queued with retry delays of 30 seconds, 1 minute, 2 minutes and so on, capped at 15 minutes. A confirmed failed model turn retries in the same persistent job session with a fresh turn identity; uncertain delivery is inspected before any resubmission. The model and profile-routing snapshot stay fixed. Retries stop after the existing 24-hour request expiry. Authentication, exhausted account quota and invalid requests remain actionable failures. Changing the local destination or clearing pending requests cancels pending saves. Only results verified within the last hour can be saved.

Each eligible result is written to its own file with the capture’s persistent request ID. If folder permission is unavailable, the pending save waits for recovery: open Folder settings and allow access again. Replaying a capture returns the existing job, preserving edits made by ApplicantAlly and respecting deleted records. Other failed or uncertain responses require checking ApplicantAlly before retrying.

Writes from the popup and keyboard shortcut are serialized inside one extension service worker and across extension contexts with a Web Lock. The tracker checks current company records immediately before writing, commits the file through a writable stream, and reads it back to confirm the capture identity. ApplicantAlly uses its existing file-store writer lock when importing and editing jobs. Tracker captures never choose Google Sheet gaps or invoke the Google Sheets Values API.

Separate browsers do not share Web Locks. Before saving, each installation obtains a durable claim from the existing local research worker for the destination ID and normalized company, then checks the actual folder records again. This prevents Chrome and SunBrowser from simultaneously adding the same company to a shared folder. Different companies can proceed independently. The worker stores ownership metadata only; the extension still reads profiles and writes job files directly. A busy or unavailable gate keeps the save pending. Claims do not expire while a browser could still resume a write; the original capture recovers its ownership after a restart. After the file operation finishes, the extension releases the claim and retries a lost acknowledgment separately.

If a result is uncertain, check the job in ApplicantAlly before trying again. Capture receipts belong to the central store; different captures are also protected by its duplicate-company check.

## Network and permissions

Runtime network access is limited to:

- LinkedIn job pages for scraping and native card dismissal, and `https://jobright.ai` / `https://www.jobright.ai` job recommendations and details for scraping and collection. No other Jobright subdomains are granted.
- `http://127.0.0.1:8787/job-research` for public captured job details, scoped research results and save-claim ownership metadata. Google credentials, candidate profiles and ApplicantAlly folder paths are not sent to this endpoint.
- Chrome’s granted folder handle for local profile choices, duplicate checks, company snapshots and saves. These operations perform no HTTP requests.
- Chrome Native Messaging for the popup’s start/status-only research helper. The helper starts the fixed local research worker; it receives no profiles or job-store data.

The extension has no Google API or arbitrary research-site permissions. The isolated local Codex session performs web research. The research worker accepts its scoped research route only from the fixed tracker extension with a private per-browser client key; browser access to its general MCP route remains blocked. The data connection uses the selected local folder and requires no ApplicantAlly API, tracker token or running ApplicantAlly process.

## Development and distribution

Run `npm test` for offline tests with synthetic local-store and research responses; retained legacy Google client tests also use generated credentials and synthetic responses. Tests never access a live account or write live jobs or a live Sheet. The legacy Google client is neither imported by the tracker nor included in its packaged extension.

Run `npm run check:version` to verify that the manifest, package and root lockfile versions match. Tests and the npm packaging command run this check automatically. Follow [CHANGELOG.md](CHANGELOG.md#versioning-policy) for release increments and record each distributed release there.

Run `npm run preview:popup` for the synthetic popup fixture. Supported modes include `?mode=unconfigured`, `?mode=offline`, `?mode=duplicate`, and `?mode=uncertain`.

Run `npm run package:extension` on Windows to create a versioned ZIP under `dist/`. Packaging uses a fixed allowlist and excludes service-account files, tests, development scripts, `.env` files, and unrelated repository content. Distribute that ZIP rather than the complete repository.
